# Rule 10.1 – Code format

> **Rule 10.1** **Use code format for identifiers, commands, file paths, and values that the reader types or sees on the screen.**

Related: [Issue 9, Rule 8.6](../../../issue-9/part-1-writing-rules/section-8-punctuation-and-word-count/rule-8-06.md) counts quoted text and alphanumeric identifiers as one word. [Issue 9, Rule 1.14](../../../issue-9/part-1-writing-rules/section-1-words/rule-1-14.md) tells you to keep the spelling of quoted text. Profile pages: [Rule 8.6](../section-8-punctuation-and-word-count/rule-8-06.md), [Rule 1.14](../section-1-words/rule-1-14.md).

## In software text

In Markdown, code format is text between backticks, for example `` `config.yaml` ``. A code span is code format in a sentence. A code block is code format on different lines, between two lines of three backticks.

Use code format for these items:

- Names from the code: functions, methods, classes, variables, parameters, configuration keys, and database tables. For example: `retry()`, `MAX_RETRIES`, the `users` table.
- Commands, command names, and flags. For example: `git`, `npm ci`, `--dry-run`.
- File names, paths, and directories. For example: `config/app.yaml`, `tests/`.
- Endpoints. For example: `/health`, `POST /users`.
- Values that the reader enters, and text that a program shows or writes to a log. For example: `true`, `30s`, `404`, `ECONNREFUSED`.

The label of a control in a user interface is quoted text, not code (Rule 8.6). Write: Click “Save.” Some types of text cannot show code format, for example a log message or the output of a program in a terminal. In these texts, use the format that the program or the project uses. If there is no format, put identifiers and values in quotation marks.

Text in code format is not a word of the STE text. Rules 1.1 to 1.13 are not applicable to it, and Rule 1.14 is not applicable to its spelling. Keep all characters of the code without a change. If the code uses `colour`, write `colour`. But do not use text in code format as a verb ([Rule 10.4](rule-10-04.md)).

Code format gives the same information to two types of readers. For a person, it shows that a word is a name from the code, not an English word, for example `kill`, `main`, or `run`. For an agent, it shows the characters that it must use or find without a change. An agent must not correct the spelling of text in code format.

Use code format only for code. Do not use it to show that a word is important. Do not use it for a technical noun that is not a name in the code: write “the database,” not “the `database`.” Code format does not make a word approved.

## Examples

- [Non-STE] Set the timeout in config.yaml to 30.
- [STE] In `config.yaml`, set `timeout` to `30`.

- [Non-STE] If you see ECONNREFUSED, the db isn't up yet.
- [STE] If the log shows `ECONNREFUSED`, the database is not available.

- [Non-STE] Set `color` to `auto` in `.toolrc`.

  (The key in the configuration file is `colour`. The writer changed the spelling to agree with Rule 1.14. Now the key is incorrect.)

- [STE] Set `colour` to `auto` in `.toolrc`.

  (Text in code format keeps its spelling.)

- [Non-STE] Examine the `database` `connection` before you `deploy`.
- [STE] Examine the connection to the database before you deploy the service.

  (“Database” and “connection” are not names from the code. “Deploy” is a technical verb. They are words of the text, not code.)

## Review notes

- Find the words that are names from the code. The same word can be an English word or a name: “the main branch” or “the `main` branch.” If you are not sure, examine the code or the product.
- Make sure that code format contains only code. A writer or an agent can put a word that is not approved in code format, and then no check finds the word. Remove the code format and examine the word with the rules of Section 1.
- Make sure that each code span has the same characters as the code. A difference of one character can cause an error when an agent uses the text.
- A mechanical check can find possible code that is not in code format, for example: an underscore (`max_retries`), uppercase letters in a word (`maxRetries`), a slash in a path, a flag that starts with `--`, parentheses after a name (`retry()`), or a file extension. Thus, the value is `suggests`. The check fails in these conditions:
  - It does not find names that are also English words, for example `main`, `status`, `kill`, and `build`.
  - It shows correct text as a possible problem, for example abbreviations, version numbers, “and/or,” and URLs in links.
  - It cannot find code format on a word that is not code.
  - An automatic correction that adds backticks can put code format on an English word, or change the text of a link.
